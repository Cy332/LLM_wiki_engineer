# 後端工程師的第二堂課 (18) 資料加速: Cache

> 原文連結：[Medium - Johnliutw](https://medium.com/johnliu-%E7%9A%84%E8%BB%9F%E9%AB%94%E5%B7%A5%E7%A8%8B%E6%80%9D%E7%B6%AD/%E5%BE%8C%E7%AB%AF%E5%B7%A5%E7%A8%8B%E5%B8%AB%E7%9A%84%E7%AC%AC%E4%BA%8C%E5%A0%82%E8%AA%B2-18-%E8%B3%87%E6%96%99%E5%8A%A0%E9%80%9F-cache-80d3cbfa69a6)
> 發布日期：2025-11-30

身為一個工程師，你可能寫過無數次的「從資料庫撈資料 -> 處理資料 -> 回傳給前端」的 API。在開發環境中，它運作良好，但在壓力測試或上線尖峰時段，你可能會收到警報：API latency、資料庫 CPU 飆高，大量使用者抱怨頁面打不開。

**這就是「效能」的問題。** 這類問題通常不在於程式邏輯寫錯了，而在於後端系統做了太多重複且成本高的工作。因此，我們可以透過快取的技術，將常用的資料儲存在另外的地方，好好替我們的應用程式加速。

最後，來一起好好了解快取吧！

## 快取的基本概念

### 1. 速度層級差

資料儲存在不同的地方，會有非常不一樣的讀取速度，我們來看看這張經典的圖片 (編按: 1ms = 1000 us, 1 us = 1000 ns):

![Image 1](https://miro.medium.com/v2/resize:fit:700/0*wDawQFvVpX-Q8tTw.jpg)

可以注意到，資料庫的讀取速度通常是在 ms 層級遊走，但是假設你的應用程式將資料安排在熱門的快取軟體 Redis，則會在 ns 的層級，其效能差距可能達到 1 萬倍以上。

而在更誇張的 CPU 層級的快取，也就是圖中的 L1/L2 Cache，更會差到百萬倍層度。而這部分的原因，跟電腦的硬體設計結構有關。

### 2. 保護後端資源系統

除了速度這個快取的核心效益，其實快取還有一個很重要的功能，也就是 — 保護後端。

假設我們有一個「熱門新聞」的 API，每秒有 1000 個請求。如果沒有快取，這 1000 個請求會全部打向你的資料庫。資料庫不僅要處理這 1000 個一模一樣的查詢，還要佔用 1000 個寶貴的資料庫連線。這會迅速耗盡資料庫的運算資源，導致其他「真正需要寫入」的操作（如用戶留言、下訂單）被卡住。

加上快取後，情況就會變成：

* 第 1 秒的第 1 個請求：沒有發現快取，查詢資料庫，將結果寫入快取。
* 第 1 秒到第 10 秒的其他 9999 個請求：因為有儲存快取，所以全部請求命中快取，直接回傳快取裡的資料。

資料庫的負載從 **1000 RPS** (Request per second) 瞬間降低到 **0.1 RPS**。你用快取保護了你最昂貴且脆弱的資料庫資源。

### 3. 成本節省

* **運算成本：** 資料庫查詢可能涉及多表 JOIN、GROUP BY、ORDER BY，這些都是高 CPU 消耗的操作。而快取存取通常是 O(1) 的簡單操作，CPU 成本極低。
* **金錢成本：** 在雲端環境中，資料庫服務，如 AWS RDS，價格較高。相比之下，快取服務如 AWS ElastiCache ，在提供同等級的查詢頻率時，更加便宜。
* **API 成本：** 如果你的服務背後依賴第三方 API，這些 API 服務通常是按次計費的。如果能將這些不常變動的結果快取起來，當然就直接省錢～

## 如何設計快取?

設計快取的機制，我們需要考量很多不同的面向，首先就要先了解「局部性原理」

* **時間局部性 (Temporal Locality)：** 剛被存取的資料，很有可能在短時間內**再次**被存取。例如，熱門新聞。
* **空間局部性 (Spatial Locality)：** 剛被存取的資料，其**附近**的資料也很有可能被存取。例如，使用者的 ID 剛被查詢，可能又會需要相關的詳細資料。

了解後，我們就來看看 3 大考量

### 1. 地點

**客戶端 (Client-Side)**

這塊就是大家最熟悉的 — 瀏覽器。其機制主要是透過 HTTP Headers（如 `Cache-Control: max-age=3600`, `ETag`）來控制快取。

適合的資源，是幾乎不變的靜態資源。例如 Logo 圖片、CSS 、JS 檔案。

這端的速度最快，因為沒有網路請求，所以根本不需要管伺服器資源，但是呢，你無法強制用戶更新快取的資料，所以就算我們開發端更新了 CSS，使用者也可能還是會看到舊版。

![Image 3](https://miro.medium.com/v2/resize:fit:700/0*mFuCrpCrEG6jjGUh.jpg)

**邊緣 (Edge)**

邊緣講起來潮，但其實就是 CDN (Content Delivery Network) 的概念。

CDN 技術，會在全球部署了大量的「邊緣節點」。使用者會請求離他地理位置最近的節點，而不是你的主機。

這部分跟客戶端一樣，適合儲存網站的靜態內容（JS/CSS/圖片），此外還有更大型的內容，像是影片串流或是整個靜態頁面，並且可以透過伺服器端控制內容版本。

邊緣的優勢是可以大幅降低全球用戶的 latency，並且吸收巨量的靜態檔案流量。但透過邊緣的缺點當然是成本相對高，畢竟常見的 CDN 都是付費服務，且不適用於高度動態的個人化內容。

**伺服器端 (Server-Side)**

伺服器端就是常見，且能夠控制範圍更大的快取地點，可以分成應用程式內快取 (In-Memory Cache) 以及分散式快取 (Distributed Cache) 兩種。

* **應用程式內快取**
  基本上就是應用程式（Tomcat, Node.js, Django…）自己所佔用的 RAM 中，畫出一塊暫存資料，雖然有極致的速度，但是因爲無法跟其他伺服器共享，且服務重啟後就消失，因此適合情境並不多，比較適合像是 config 的快取
* **分散式快取**
  ![Image 4](https://miro.medium.com/v2/resize:fit:513/0*75tLMNsHShXbVrVK.png)
  透過一個或多個獨立的、專門用來快取的伺服器，像是 Redis 或 Memcached 等知名軟體，讓我們的 10 台伺服器，全都連到「同一個」Redis 服務去存取資料。
  最顯著的優點就是共享，所有伺服器共享一份快取資料，效益最高。另外就是高可用，快取可獨立擴展、有備援機制，服務重啟快取也不會丟失。
  但缺點來說，就是需要一次網路 I/O，速度略遜於 In-Memory，但仍遠快於資料庫。

### 2. 模式

這部分的設計思考著重在什麼時機去讀寫快取，才恰當。主要可以分成三種

![Image 5](https://miro.medium.com/v2/resize:fit:700/0*rE9MvlCnkSkTPmrt.png)

#### Cache-Aside
這是最常見，經典的模式，適合大部分讀多寫少的系統場景，例如部落格、電商產品，可以容忍輕微的資料延遲，讀到舊資料也沒關係。

**讀取流程**
- a. 應用程式先嘗試從快取讀取資料
- b-1. 如果成功，直接回傳資料
- b-2. 如果失敗，應用程式會繞過快取，改從資料庫讀，並且順便將資料寫到快取

**寫入流程**
- a. 應用程式直接將資料寫到資料庫
- b. 應用程式刪除快取，等到下次有人讀取時，更新快取

這邊我們可以注意到，用刪除的好處時，假設短時間內沒有人讀取，但是卻快速寫入了 10 次，則只會有 10 筆刪除的「指令」。如果是用更新的，就會變成要做 10 次更新資料，而且前 9 筆都是無效的。

![Image 6](https://miro.medium.com/v2/resize:fit:700/0*iPipw-KGgFi263HF.png)

#### Write-Through
在 Write-Through 中，應用程式被「簡化」了。它假裝資料庫不存在，只對快取進行操作。快取服務本身承擔了保持資料庫同步的責任。

因此，適合絕對要求資料一致性的系統，例如金融交易相關，你不會希望一筆交易後，餘額竟然還是錯誤的資料吧? 但當然的，其效能會較差一些。

**讀取流程**
- a. 應用程式先嘗試從快取讀取資料
- b-1. 如果成功，直接回傳資料
- b-2. 如果失敗，快取會從資料庫讀取資料，並且寫入快取內部，再回傳給應用程式

**寫入流程**
- a. 應用程式將資料寫入快取
- b. 快取用「同步」的方式，將資料寫入後端資料庫
- c. 確定資料庫寫入成功，才回報給應用程式成功

可以注意到，由於要用同步的方式，所以寫入的延遲會相對高，因此 Redis/Memcached 等服務其實預設是不支援此模式的。

![Image 7](https://miro.medium.com/v2/resize:fit:700/0*Rk-nfkpVtq_v0ni4.png)

#### Write-Back (Write-Behind)
Write-Back 是一種以快取為尊的模式，追求極低的寫入延遲，沒有在管其他問題，非常適合 IOT 資料搜集、監控指標更新等系統。

**讀取流程 (相同於 Write-through)**
- a. 應用程式先嘗試從快取讀取資料
- b-1. 如果成功，直接回傳資料
- b-2. 如果失敗，快取會從資料庫讀取資料，並且寫入快取內部，再回傳給應用程式

**寫入流程**
- a. 應用程式將資料寫入快取
- b. 快取直接跟應用程式說寫入成功，應用程式可以先去做下一件事
- c. 快取「非同步」的方式，批次將資料寫到資料庫中

你可以注意到，這樣的模式，就算資料庫掛掉一陣子也沒事，等下次批次任務執行即可，所以寫入吞吐量超高。
但是呢，假設反過來是快取當機，就有可能導致快取中的資料遺失，造成狀態不一致的問題，而且此類型的實作複雜度也較高。

### 3. 更新 (Eviction Policies)

快取的記憶體是有限的。當快取滿了，必須丟掉一些舊資料，才能放入新資料。丟掉誰呢？

* **TTL (Time-To-Live)：** 最簡單的策略。設定一個存活時間，例如 30 分鐘。時間一到，自動刪除
* **LRU (Least Recently Used)：** 依據「時間局部性」，找出最近最少使用的資料，邏輯是，如果一個資料很久沒被存取了，那它未來被存取的機率也很低。因此，當快取滿了時，就丟掉那個最久沒被讀取的資料。這是 Redis 和 Memcached 最常用的策略之一。
* **LFU (Least Frequently Used)：** 跟 LRU 很像，找出**最不常使用的資料**。邏輯是依據「熱門度」，如果一個資料雖然剛剛被存取過（LRU 不會丟它），但它歷史上的總存取次數很少，那它可能不如其他總是很熱門的資料重要。因此，當快取滿了，丟掉那個「被存取次數最少」的資料。
* **FIFO (First-In, First-Out)：** 先進先出。像排隊一樣，最先進來的最先被丟掉，不管它熱不熱門。效能通常最差，但適合事件串流、日誌處理或是一次性通知相關系統，因為先來的通常就不重要的，丟掉也沒關係

## 快取實際上會發生的問題

### 什麼資料該快取

簡單來說，最值得的場景如下:
* 讀取遠大於寫入 (Read-heavy)，如新聞文章、商品資訊、用戶個人資料
* 資料穩定，如網站 config 、地區代碼、分類列表
* 計算昂貴的結果，如複雜的統計報表、推薦演算法結果
* 第三方 API 結果，如天氣、匯率

而通常較不值得的呢，會是:
* 寫入極度頻繁 (Write-heavy)，如股票即時價格
* 資料準確性極高，如銀行帳戶餘額
* 高度敏感資料，因為快取層安全性防護相對不足，如密碼、信用卡號
* 巨量資料但存取不頻繁，導致快取命中率低，例如 Log

### 快取的災難事件

![Image 8](https://miro.medium.com/v2/resize:fit:700/0*PN17sAvlcIryHhsr)

1. **快取穿透 (Cache Penetration)**
   此問題為大量 request 湧入，查詢一個資料庫和快取都「不存在」的資料。例如，爬蟲或惡意攻擊者，用 `user_id = -1, -2, -3...` 這種不存在的 ID 瘋狂請求你的 API。
   因為每次請求都會執行 Cache-Aside 的「未命中」邏輯，全部打穿到資料庫去執行 SQL Query，資料庫會被這些查詢無情的擊垮。
   * **防禦思維**: 針對這種問題，當你從資料庫查詢後，發現結果是空，例如 null 或 empty，也把這個「空結果」快取起來，並且給予短一點的 TTL，防止它佔用太多記憶體，也讓資料未來有機會被建立。
2. **快取擊穿 (Cache Breakdown)**
   快取中某一個極度熱門的 Key，又叫做 Hot Key，在它失效的那一瞬間，湧入了成千上萬的 requests。例如，雙 11 時某個超熱賣商品的快取時間剛好在行銷活動剛開始失效。
   而由於這上萬個請求會同時未命中，然後同時去請求資料庫，很有可能導致資料庫瞬間崩潰。
   * **防禦思維**：透過互斥鎖 (Mutex Lock) 的技術。當一個請求發現未命中時，它先去取得一個鎖，而我們在快取設定說，只有拿到這個鎖的 request，能去查詢資料庫和更新快取。其他沒搶到鎖的 request，則稍微等候一下再重試，而此時第一個 request 很可能已經把快取更新好了。
3. **快取雪崩 (Cache Avalanche)**
   這部分跟快取擊穿類似，只是是「大量」的 Key 在同一時間集體失效，常發生在所有的 Key TTL 都是一樣的狀況。或者更糟，快取伺服器直接掛掉。
   後果呢，因為幾乎所有的請求都「未命中」，瞬間的全部流量都湧向資料庫，造成資料庫雪崩式崩潰。
   * **防禦思維**: TTL 應該要是隨機的，可以設定類似 `ttl = 3600 + random.randint(0, 300)` 的邏輯。並且針對快取伺服器，仔細打磨高可用的特性，或是讓應用程式在快取伺服器掛掉時，可以先降級，拒絕部分功能。

最後，請記住，快取的使用不是必要，先思考該怎麼測量系統的效能瓶頸，真的有問題，也先設定簡單架構，並繼續監控重要指標，例如快取命中率，才能確保你的效能優化工具，好好生效中喔！
